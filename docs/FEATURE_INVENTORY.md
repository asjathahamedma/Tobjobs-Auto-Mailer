# Feature Inventory and Web Mapping

This inventory records existing behavior and its intended web destination. “Planned” is not a claim that the web feature is already implemented. Preserve existing behavior where it is safe and technically suitable; make workflow safety changes explicit.

This is a historical desktop feature inventory. See [the current web migration status](./MIGRATION_PLAN.md) for the implementation and remaining validation gaps.

| Feature | Existing behavior and source | Web mapping / migration decision |
|---|---|---|
| Account registration and login | Local one-account-per-device flow in `desktop_app/account_service.py`; salted PBKDF2 hash in `data/account.json`; frontend auth is transient React state. | Replace with Supabase Auth, secure server-managed session cookies, protected pages/API, logout, and authorization derived from the verified session. Do not transfer the local password hash as a Supabase password. |
| First-run setup | `ui/src/pages/WelcomePage.tsx` collects name/contact email and Gmail sender/App Password. | Web onboarding form writes user-owned profile/settings; keep SMTP secret entirely server-side and never echo it to the browser. |
| Supported job source | TopJobs.lk category listings and advert pages only (`src/scraper.py`); defaults are two functional-area URLs. | Preserve as a source adapter behind a normalized job interface. Add other sites only after separate permission/terms and parser review. |
| Job discovery | HTTP GET + HTML parsing of category rows, dates, title, advert URL; details page extraction includes visible text, company email, and image links. | Keep real TopJobs logic in a Python service/module and persist each result incrementally. Add company, location, salary, employment type, description, and stable source identifiers only where source data actually provides them. |
| HTTP resiliency | GET session retries selected transient status codes and network failures; request timeouts; one advert failure is logged and skipped. | Retain source-specific timeout/retry behavior, add bounded request limits, request IDs, per-item error records, and avoid arbitrary user-provided fetch URLs. Label raw points accurately; do not display as a percent unless a calibrated conversion is implemented. |
| Search filters | Recent window, remote-only, minimum score, seniority/exclusion keywords, OCR flag, languages, and category URLs in local JSON settings. | Store validated per-user settings in Postgres. | Application email generation | Template-based professional subject/body using job title, profile summary, matched keywords and contact details. | Preserve as editable draft content; display job and recipient for explicit review before any send. |
| Cover letters | Template-generated PDF via ReportLab; optional attachment to application email. | Preserve generation/download, use per-user resume/profile and job data, store generated file privately only if needed. No AI provider is currently configured. |
| Application sending | SMTP Gmail App Password; email sent automatically for matched lead if recipient and resume path are present. Use idempotent submission records and distinguish “SMTP accepted” from employer delivery. Provide manual copy/download fallback. |
| Duplicate protection | `data/processed_jobs.csv` tracks previously sent URLs; scraper skips these URLs. Local SQLite `jobs.url` is a primary key. | Use canonicalized source URL and database uniqueness; add a unique application guard per user/job or explicit retry policy. Make run retries idempotent. |
| Job/application list | Desktop list combines recent leads and feedback; search/status/profile/date filters; currently local snapshot only. | Build server-paginated job list with server-side filtering/sorting, detail view, original URL, discovered date, match evidence, and application status. |
| Job detail | Current list has limited fields; no dedicated full-detail page. | Add a dedicated route with available source fields, match explanation, requirements, original link, review actions and history. |
| Application tracker | CSV/SQLite records of sent, skipped, and failed attempts; no complete user-editable lifecycle. | Add persistent statuses (discovered, shortlisted, awaiting review, ready, applied, interview, rejected, withdrawn, failed), notes, timestamps, status audit, and manual updates. | Dashboard and analytics | Local logs/CSVs and SQLite-derived metrics: scan totals, matching, skipped reasons, applications, profile performance and recent activity. Do not delete published GitHub releases before the web version and data export are verified. |
| Notifications | No email/push notification subsystem found. | Out of scope unless requested; if added, use explicit preferences and server-side provider configuration. |

## Important behavior changes requiring user-visible treatment

1. The desktop currently sends matched-job emails automatically. The web edition must instead present generated content, destination, job details, and an explicit approval action before SMTP sends.
2. SMTP acceptance is not proof of employer receipt or a job-site submission. UI status names and analytics must reflect that distinction.
3. Local desktop authentication does not protect data across devices. Supabase Auth plus RLS and server authorization are required before public deployment.
4. Match scores are weighted keyword points, not probability or fit percentage. Preserve the evidence and clearly label scores.
5. Existing analytics are reconstructed from logs/CSV artifacts in part; a web edition should use durable structured run/job/application rows as its source of truth.
